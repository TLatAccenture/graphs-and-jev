Agentic migration and modernisation

Give migration agents the right tools for the job.

Most enterprise estates grew over decades: storage in AWS and Azure, platforms such as SAP, Salesforce, Databricks, ServiceNow and Atlassian, and years of Word, Excel and PowerPoint files in Microsoft 365. Migrating that estate with agents needs a different approach, one that counts what the work costs today and what the result will cost to run tomorrow. We call that approach the MCP shed.

The problem

Agents need the right tools for the job.

Many systems, no single map

Enterprises rarely have one system of record. They have many, each with its own interface, credentials and quirks, and the knowledge of how they connect often lives in people's heads or in one-off scripts. An agent dropped into that estate either sees too little to act safely, or is handed so many tools and so much context that it slows down, costs more and makes confident mistakes.

Why now

Context windows keep growing (Google, long context), but well-architected agents still need careful context management: models use information in the middle of long prompts less well (Lost in the Middle), and tool definitions and results consume the window (Anthropic, code execution with MCP; Anthropic, context engineering). The Model Context Protocol has become the common standard for connecting agents to tools (MCP specification): a shared language for networked function calling, much as APIs were for the previous generation of systems. It has its critics, but adoption has largely settled the argument. Stripe's in-house coding agents, Minions, now merge more than a thousand pull requests a week (Stripe), drawing on a central MCP server reported to expose over 400 tools (VirtusLab, secondary report). We expect the same shift in enterprise migration and modernisation.

The approach

Five pillars, one stack.

The MCP shed is a governed, curated set of MCP servers that gives each migration agent the tools its task needs, and nothing more. Around it sit four further layers: fast decision models that gate each step, prescriptive playbooks, a graph of lineage and meaning, and measurement that shows what the agents did and what it cost.

Each layer builds on the one beneath it. Select a layer to open it.

  1. Each system in the estate is reached through an MCP server with scoped, short-lived credentials and an audit trail. Agents receive only the servers their task needs, which keeps tool definitions out of the context window and secrets out of scripts.

    Go deeper: connectivity

  2. Spanner Graph, or another graph engine, records which tables, jobs, files and reports feed which others, and what each business term means. Before an agent changes anything, it can see what sits upstream and downstream, so a change in one place does not silently break another.

    Go deeper: relational context

  3. Skills give agents a prescriptive playbook for each migration pattern. Hooks run before and after tool calls to validate schemas, block unsafe actions and require approval where needed. Together they reduce drift, broken code and malformed schemas.

    Go deeper: logic

  4. A System 1 model such as Jev, TypeSafe's System 1 decision model, returns a typed decision with a calibrated confidence. TypeSafe reports end-to-end response times of 70 to 500 ms (TypeSafe, vendor-reported), against seconds for a frontier model, fast enough to sit in front of every tool call. It does not make a model stop hallucinating; it stops an uncalibrated output from becoming an action.

    Go deeper: reflexes

  5. Every agent step writes an eval record: decision, confidence, tools called, tokens, latency and outcome. Engineers use the records to find failure patterns. BigQuery and Looker turn them into production reporting for users, including cost per migrated object, so the spend today and the run cost tomorrow are both visible.

    Go deeper: visibility and cost

Terms used on this site

MCP
Model Context Protocol. An open standard for connecting AI applications to tools, resources and live systems (MCP specification).
MCP server
A service that exposes one system's tools and data to agents over MCP, for example a CMDB, a data warehouse or a document store.
MCP shed
The governed set of MCP servers available to migration agents, with each agent given only what its task needs.
Skill
A packaged playbook an agent loads for a specific task, such as migrating a table or converting a batch job.
Hook
A check that runs automatically before or after a tool call and can block it.
System 1 model
A small, fast model that returns a typed decision with a calibrated confidence instead of free text (TypeSafe). Jev is an example.
Lineage graph
Facts (nodes) and typed relationships (edges) recording which data, code and reports feed which others.
Eval record
A structured log of one agent step: decision, confidence, tools, tokens, latency, outcome.

Governance

Built to show its working, and to say no.

  • Least privilegeEach agent gets only the MCP servers and scopes its task needs.
  • Refusal before tool callUnsafe requests, such as copying production customer data to a test environment, stop before any server is called.
  • Bounded outcomesProceed, ask, refuse, escalate or no data. Nothing in between.
  • TraceableEvery outcome returns the lineage path and the evidence behind it.
  • MeasuredEvery step writes an eval record, including tokens and latency.
  • PortableStatic pages and a documented API contract. The same pages run from in-browser fixtures or from a Rust service on Cloud Run that serves the pages and the API from one origin.

The demonstrations use a small in-memory graph and deterministic rules. They are illustrative, not a production migration tool.
