Pillar 1 · Connectivity

Governed MCP servers replace one-off scripts.

Each system in the estate is reached through an MCP server with scoped, short-lived credentials and an audit trail. Agents receive only the servers their task needs, which keeps tool definitions out of the context window and secrets out of scripts.

Pillar 2 · Relational context

A graph of lineage and meaning.

Spanner Graph, or another graph engine, records which tables, jobs, files and reports feed which others, and what each business term means. Before an agent changes anything, it can see what sits upstream and downstream, so a change in one place does not silently break another.

Spotlight

Google Cloud Spanner Graph

One database. Relational and graph views.

Spanner Graph maps Spanner tables or SQL views into a property graph without creating a separate copy of the data. Teams can use GQL for graph patterns, SQL for relational work, and combine both when a decision needs connected and tabular context.

  • Google Cloud describes it as multi-model: a property graph schema is defined declaratively over existing tables or views. It needs the Enterprise or Enterprise Plus edition.
  • Graph queries use an ISO GQL-compatible interface.
  • GoogleSQL can read graph matches through GRAPH_TABLE, so graph and relational results meet in one query.
  • The graph inherits Spanner’s scale, availability and strong consistency.

Capabilities are summarised from Google Cloud documentation. The grades and scores below are this site’s independent judgement; this spotlight does not change them, and Spanner Graph keeps its evidence-based B grade. Jev, TypeSafe's System 1 decision model, is not a Google Cloud product.

Strong fit

  • Operational data already lives in Spanner.
  • The application needs relational and relationship queries over the same data.
  • Strong consistency and managed multi-region operation matter.
  • The organisation prefers a managed Google Cloud database platform.
  • Graph context should stay next to transactional facts, not in a separately synchronised store.

Consider carefully

  • It is a Google Cloud service, not a portable or embedded database.
  • Cost and capacity follow the Spanner operating model.
  • Validate schema mapping, query shape, latency and traversal depth with representative data.
  • Test the GQL features and graph algorithms you need; do not assume parity with graph-native products.
  • A dedicated graph store may still suit some graph-first workloads better.

Browser labs on the sample estate

Both labs run in your browser on the 15-fact sample estate used by the guided example on the landing page: SAP, BigQuery, Databricks, Looker, Salesforce and SharePoint objects joined by lineage edges. Change the settings, or open the code, edit it and run your version.

Lab 1: hybrid text retrieval against graph retrieval

The text baseline is what most teams already run: BM25 over each node's text, fused by reciprocal rank fusion with dense similarity from a small embedding model (all-MiniLM-L6-v2). Dense similarities for the four preset questions are precomputed by scripts/dense.py; for a question you type yourself, the text side falls back to BM25 alone. Graph retrieval starts at the entities named in the question and follows relationships.

Pillar 3 · Logic

Playbooks as enforced steps.

Skills give agents a prescriptive playbook for each migration pattern. Hooks run before and after tool calls to validate schemas, block unsafe actions and require approval where needed. Together they reduce drift, broken code and malformed schemas.

Pillar 4 · Reflexes

Fast models gate every step.

A System 1 model is a small, fast model that returns a typed decision with a calibrated confidence instead of free text. TypeSafe calls this class System One models [L8]. Jev takes a state and a set of typed questions, and returns typed answers with probabilities and a confidence that code can branch on [L9].

A System 1 model such as Jev returns a typed decision with a calibrated confidence. TypeSafe reports end-to-end response times of 70 to 500 ms [L8] Vendor-reported, against seconds for a frontier model, fast enough to sit in front of every tool call. It does not make a model stop hallucinating; it stops an uncalibrated output from becoming an action.

An independent review measured a 524 ms median for a hosted round trip [L10].

Lab 3: calibrated decisions with per-action thresholds

A simulation of a confidence-gated decision loop. No model is called. Each case gets a stated confidence; it is decided automatically if the confidence clears that action's threshold, otherwise it goes to review at a cost of 1. The error costs (50, 2 and 5), the review cost and the 3,000 cases are illustrative; the thresholds are assumptions you can edit. Raise overconfidence to see what happens when stated probabilities stop matching reality.

Pillar 5 · Visibility and cost

What agents did, and what it cost.

Every agent step writes an eval record: decision, confidence, tools called, tokens, latency and outcome. Engineers use the records to find failure patterns. BigQuery and Looker turn them into production reporting for users, including cost per migrated object, so the spend today and the run cost tomorrow are both visible.

Three Looker tiles, in words

Built in Looker over the table above [L12]. No figures are shown because none have been measured.

  1. Cost per migrated object. Sum of cost_usd divided by the count of distinct object_id values whose final step ended in answer, by week. It shows whether migration is getting cheaper per object as skills and thresholds improve.
  2. Outcomes by step. A stacked bar of step counts by step, split by outcome code (answer, clarify, reject, review, no_data, shown to users as Proceed, Ask, Refuse, Escalate and No data). It shows where in the playbook agents stop, and why.
  3. Escalation rate by skill. The share of steps with outcome review for each skill, with the median confidence alongside. A rising rate points to a playbook or threshold that needs attention.
