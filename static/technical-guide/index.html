Layer 1 · MCP Tool Shed · Connectivity

Governed MCP servers replace one-off scripts.

One MCP server per system, with scoped, short-lived credentials and an audit trail. Agents get only the servers they need. No spare tool definitions in context, no secrets in scripts.

Layer 2 · System 1 (Jev) · Reflexes

Fast models gate every step.

A System 1 model is small and fast. It returns a typed decision with calibrated confidence, not free text. TypeSafe calls these System One models [L8]. Jev takes a state and typed questions, and returns typed answers, probabilities and a confidence that code can branch on [L9].

TypeSafe reports 70 to 500 ms end to end [L8] Vendor-reported, against seconds for a frontier model. Fast enough to gate every tool call. It does not stop hallucination; it stops uncalibrated output becoming action.

An independent review measured a 524 ms median for a hosted round trip [L10].

Lab 3: per-action confidence thresholds

A simulated confidence gate; no model is called. A case is automated if its confidence clears the action's threshold, else reviewed at a cost of 1. Error costs (50, 2 and 5), review cost and 3,000 cases are illustrative; thresholds are editable assumptions. Raise overconfidence to watch calibration break.

Layer 3 · Gemini Enterprise Agent Platform · Skills and hooks

Playbooks as enforced steps.

Skills give agents a fixed playbook per migration pattern. Hooks run around tool calls to validate schemas, block unsafe actions and require approval. Less drift, broken code and malformed schemas.

Layer 3 · Context fabric: Spanner Graph · Relational context

A graph of lineage and meaning.

A graph engine such as Spanner Graph records lineage across tables, jobs, files and reports, and what each business term means. Agents check upstream and downstream before any change.

Spotlight

Google Cloud Spanner Graph

One database. Relational and graph views.

Spanner Graph maps tables or SQL views into a property graph without copying data. GQL for graph patterns, SQL for relational work, or both.

  • Multi-model, per Google Cloud: a property graph schema declared over existing tables or views. Needs Enterprise or Enterprise Plus edition.
  • Graph queries use an ISO GQL-compatible interface.
  • GoogleSQL reads graph matches through GRAPH_TABLE, so graph and relational results meet in one query.
  • It inherits Spanner’s scale, availability and strong consistency.

Capabilities are from Google Cloud documentation. Grades and scores below are this site’s independent judgement. This spotlight does not change them; Spanner Graph keeps its evidence-based B grade. Jev, TypeSafe's System 1 decision model, is not a Google Cloud product.

Strong fit

  • Operational data already lives in Spanner.
  • You need relational and relationship queries over the same data.
  • Strong consistency and managed multi-region matter.
  • You prefer a managed Google Cloud database.
  • Graph context should sit next to transactional facts, not in a synced copy.

Consider carefully

  • It is a Google Cloud service, not portable or embedded.
  • Cost and capacity follow Spanner’s model.
  • Test schema mapping, query shape, latency and traversal depth on representative data.
  • Test the GQL features and graph algorithms you need; do not assume parity with graph-native products.
  • A dedicated graph store may suit some graph-first workloads better.

Lab 1: hybrid text against graph retrieval

The usual text baseline: BM25 over node text plus all-MiniLM-L6-v2 dense similarity, fused by reciprocal rank fusion. scripts/dense.py precomputes dense scores for the four presets; typed questions use BM25 only. Graph retrieval follows relationships from the named entities.

Layer 4 · Modernisation Springboard · Visibility and cost

What agents did, and what it cost.

Every agent step writes an eval record: decision, confidence, tools called, tokens, latency and outcome. Engineers mine them for failure patterns. BigQuery is the destination lakehouse for migrated data and the store for telemetry, audit logs and these records. Looker reports cost per migrated object: today's spend and tomorrow's run cost.

Three Looker tiles

Built in Looker over this table [L12]. No figures shown; none have been measured.

  1. Cost per migrated object. cost_usd summed over distinct object_id values whose final step ended in answer, by week. Is it falling as skills and thresholds improve?
  2. Outcomes by step. Step counts by step, stacked by outcome (answer, clarify, reject, review, no_data; shown as Proceed, Ask, Refuse, Escalate and No data). Where agents stop, and why.
  3. Escalation rate by skill. Share of steps with outcome review per skill, with median confidence. A rise flags a playbook or threshold to fix.
